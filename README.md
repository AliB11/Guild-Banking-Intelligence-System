میز کار شاپرک، اطلس رسته، ماشین‌حساب کارمزد کارتخوان، دفترچه منابع و به‌روزرسانی ماهانه پس از انتشار گزارش شاپرک.

> **حالت اصلی: کاملاً بدون دیتابیس.** برنامه یک وب‌اپ استاتیک است که جمعِ منتشرشدهٔ شاپرک/بانک مرکزی/اینتا را به‌صورت درون‌برنامه‌ای محاسبه می‌کند؛ بدون PostgreSQL، بدون سرور Node، بدون متغیر محیطی — روی GitHub Pages با یک کلیک. نام پذیرنده و رسوب CASA در منبع عمومی نیست و ساخته نمی‌شود.

## اجرای سریع (بدون دیتابیس)

```bash
npm install
npm run dev        # توسعه روی http://localhost:3000
```

ساخت و اجرای نسخه تولیدی:

```bash
npm run build      # خروجی استاتیک در ./out
npm start          # سرو out/ + API اختیاری (بدون دیتابیس: حالت demo)
```

- تمام صفحات در مرورگر روی corpus منتشرشده (`src/lib/gbi/published-market.ts`) کار می‌کنند؛ هیچ فایل `.env` لازم نیست.
- آخرین ماهنامه شاپرک در این نسخه **مرداد ۱۴۰۵** (گزارش ۱۳۴) است. شهریور در تقویم جاری است اما رقم شاپرک ندارد و به‌عنوان دوره جاری نمایش داده نمی‌شود.
- قیف سرنخ، BCG، نقشه استان و تالار پذیرنده در محصول نیستند چون داده عمومی ندارند.

## استقرار روی GitHub (GitHub Pages)

Workflow `Deploy to GitHub Pages` (.github/workflows/pages.yml) روی هر push به `main` خروجی استاتیک را با `NEXT_BASE_PATH` خودکار (از نام repository) build و روی Pages منتشر می‌کند.

فعال‌سازی (یک‌بار):

1. در repository: **Settings → Pages → Build and deployment → Source: GitHub Actions**
2. روی `main` push کنید؛ site روی `https://<owner>.github.io/Guild-Banking-Intelligence-System/` آنلاین می‌شود.

بدون دیتابیس، بدون secret، بدون env — فقط خود repository. برای انتشار از branch دیگر یا تست دستی: **Actions → Deploy to GitHub Pages → Run workflow**. اگر از دامنه سفارشی استفاده می‌کنید، مقدار `NEXT_BASE_PATH` در workflow را خالی بگذارید (ریشه دامنه).

## معماری دو حالتی

| حالت | داده | اجرا | کاربرد |
| --- | --- | --- | --- |
| **استاتیک** (پیش‌فرض) | ماهنامه شاپرک + طبقه‌بندی ISIC/INTA/MCC | فایل‌های خالص HTML/JS — GitHub Pages، هر host استاتیک، یا `npm start` | دمو با ارقام منتشرشده، بدون زیرساخت |
| **full-stack اختیاری** | PostgreSQL (Drizzle) + audit/outbox | Node server خالص (`src/server/server.ts`) با همان قرارداد JSON | داده واقعی، Docker/compose |

- `src/lib/gbi/compute.ts` — همه محاسبات (pure)؛ دقیقاً توابع یکسانی هم در مرورگر و هم در سرور اجرا می‌شوند.
- `src/lib/gbi/client-data.ts` — لایه داده مرورگر (بدون هیچ وابستگی نودی).
- `src/lib/gbi/service.ts` + `src/db` — facade سرور؛ فقط در حالت PG لود می‌شود (pg/drizzle وارد باندل مرورگر نمی‌شوند).
- `src/server/server.ts` — سرور HTTP نود (بدون فریم‌ورک) که `out/` را سرو می‌کند و APIهای JSON را در دسترس نگه می‌دارد:

| endpoint | توضیح |
| --- | --- |
| `GET /api/health` | وضعیت: `demo` (بدون DB) یا `postgres` (قابل‌دسترس / بدون migration / ناپایدار) |
| `GET /api/dashboard` | شاخص‌های مدیریتی |
| `GET /api/guilds` | طبقه‌بندی رسته‌ها (اختیاری) |
| `GET /api/leads` | در حالت استاتیک خالی است |
| `POST /api/calculator` | موتور کارمزد/تسهیلات |
| `GET /api/catalog` | کاتالوگ منابع، تقویم انتشار و ماهنامه |

## اجرای Docker / GHCR (حالت full-stack اختیاری)

Workflow `CI` روی هر push و Pull Request، lint، typecheck و build را اجرا می‌کند. Workflow `Publish container` روی `main` یا tag نسخه، image را در `ghcr.io/<owner>/<repository>:latest` منتشر می‌کند:

```bash
docker compose up --build -d
docker compose --profile seed run --rm seed   # اختیاری؛ داده demo را جایگزین می‌کند
```

Container همان سرور نود را با `RUN_DB_MIGRATIONS=true` و healthcheck `/api/health` اجرا می‌کند. بدون `DATABASE_URL`، container نیز بدون دیتابیس (حالت demo) کار می‌کند.

## به‌روزرسانی ماهانه پس از انتشار اصناف

Workflow `Monthly guild catalog refresh` (`.github/workflows/monthly-refresh.yml`) روزهای ۳، ۸، ۱۲، ۱۸ و ۲۵ هر ماه میلادی اجرا می‌شود — یعنی بعد از تأخیر معمول انتشار گزارش شاپرک و بستن ماه بانک:

1. صفحهٔ هر منبع رسمی را واکشی و اثرانگشت (hash) را ذخیره می‌کند.
2. اگر هش عوض شده باشد **ارقام را سرخود جایگزین نمی‌کند**؛ پرچم بازبینی انسانی می‌زند.
3. پنجرهٔ گزارش را با آخرین ماه **منتشرشده** شاپرک هم‌تراز می‌کند و **ماهنامه هوش اصناف** را بازتولید می‌کند.
4. در صورت تغییر معنادار، `public/data/intelligence-catalog.json` را commit می‌کند تا GitHub Pages هم به‌روز شود.

اگر سایت‌های ایران از رانر GitHub در دسترس نباشند جاب شکست نمی‌خورد؛ وضعیت `unreachable` در کاتالوگ دیده می‌شود. اجرای دستی از Actions → Monthly guild catalog refresh → Run workflow.

## قرارداد محاسباتی مهم

تمام مبالغ در لایه داده و موتور محاسباتی **ریال** هستند و فقط در لایه نمایش به تومان تبدیل می‌شوند. `GET /api/health` در حالت واقعی اتصال PostgreSQL و در حالت بدون پیکربندی، وضعیت demo را گزارش می‌کند.

## موارد اصلاح‌شده در بازبینی ۳۶۰ درجه

- حذف خطای build ناشی از پرتاب `DATABASE_URL is required` هنگام import شدن ماژول دیتابیس؛ اتصال اکنون lazy است و حالت نمایشی کنترل‌شده دارد.
- اضافه شدن fallback کامل و قابل مشاهده برای اجرای UI در checkout تازه، به‌علاوه error/loading boundary.
- جلوگیری از race condition ماشین‌حساب؛ پاسخ قدیمی شبکه دیگر نتیجه سناریوی جدید را overwrite نمی‌کند.
- اصلاح ROI از «درآمد ناخالص / هزینه» به «حاشیه خالص / هزینه».
- اصلاح مقدار پیش‌فرض سبد خرید که با واحد اسلایدر (تومان) هم‌خوان نبود.
- جلوگیری از setState در render در پنل مقایسه و حذف setState همگام داخل effect کانبان.
- optimistic update امن برای جابه‌جایی سرنخ با rollback هنگام خطا و آمار لحظه‌ای ستون‌ها.
- اصلاح محاسبه میانگین امتیاز رسته‌ها در حضور پذیرنده بدون metric دوره جاری.
- اصلاح سهم بازار رادار از «نرمال‌شده نسبت به بزرگ‌ترین رسته» به سهم واقعی از کل گردش.
- جلوگیری از درصد رشد جعلی در اولین دوره و محدود کردن روند به شش دوره اخیر.
- نمایش دو محور واقعی برای نمودار گردش/رسوب، empty state برای نمودارهای بدون داده و پشتیبانی از reduced motion.
- افزودن unique index برای `(merchant_id, reporting_period)` و تبدیل Drizzle config به تنظیمات مبتنی بر env.
- اصلاح timestampهای seed که قبلاً سال جلالی را مستقیماً به `Date` میلادی می‌دادند.
- ارتقای Next/PostCSS به نسخه‌های بدون آسیب‌پذیری runtime گزارش‌شده و اضافه شدن بررسی health.
- **استقرار بدون دیتابیس:** تبدیل اپ به static export با لایه داده کلاینت‌ساید؛ حذف وابستگی اجباری به PostgreSQL و افزودن workflow GitHub Pages (جزئیات در `docs/feasibility-github-pages.md`).
- **تبار داده و به‌روزرسانی ماهانه:** صفحه منابع، واژه‌نامه ساده، راهنمای خواندن هر صفحه، جاب واکشی پس از انتشار گزارش اصناف، و ماهنامه خودکار (جزئیات در `docs/sources.md` و `docs/360-review.md`).

## قابلیت‌های عملیاتی اجراشده

بخش اول پیشنهادها همین حالا در سامانه فعال است:

- **Next Best Action:** هر سرنخ اکنون اقدام بعدی، دلیل، سطح فوریت و SLA دارد؛ آمار «اقدام فوری» نیز در کانبان محاسبه می‌شود.
- **آزمایشگاه شوک نقدینگی:** در ماشین‌حساب، افت گردش/سبد، تغییر رسوب، CCC و هزینه پشتیبانی به‌صورت تعاملی روی حاشیه و سقف اعتبار شبیه‌سازی می‌شوند.
- **نقشه فرصت شعب:** شعب بر اساس گردش، رسوب، انطباق و پوشش سرنخ رتبه‌بندی و به اقدام‌هایی مثل توسعه POS یا کمپین اعتبار متصل شده‌اند.
- **هشدار زودهنگام:** افت گردش، تمرکز ریسک، شکاف مالیاتی و سرنخ‌های خارج از SLA در داشبورد نمایش داده می‌شوند.
- **Data Quality Gate:** orphan، duplicate، مقدار منفی و نبود metric دوره جاری پیش از نمایش KPI شمارش و امتیازدهی می‌شوند.
- **Explainability:** نسخه مدل و مفروضات نرخ/ذخیره/اسپرد در خروجی ماشین‌حساب قابل مشاهده است و دلیل اقدام سرنخ به‌صورت rule-based برگردانده می‌شود.
- **ماتریس BCG رسته‌ها:** صفحه اصناف، رسته‌ها را در چهار ربع ستاره، گاو شیرده، علامت سؤال و سگ نشان می‌دهد؛ سهم نسبی گردش روی محور افقی، رشد گردش روی محور عمودی و اندازه/رنگ حباب بر اساس حاشیه خالص بانک است. وضعیت هر حباب نیز سودده، مرزی یا زیان‌ده نمایش داده می‌شود.
- **Audit و Outbox:** تغییر مرحله سرنخ در PostgreSQL داخل transaction با رویداد audit و outbox ثبت می‌شود تا اتصال بعدی به CDC/صف پیام بدون تغییر منطق کسب‌وکار انجام شود.
- **دفترچه منابع و ماهنامه:** صفحه منابع می‌گوید هر عدد از کجاست؛ جاب GitHub بعد از انتشار گزارش اصناف صفحه منبع را واکشی می‌کند و ماهنامه را بازتولید می‌کند.

## روش و محدودیت ماتریس BCG اصناف

ماتریس BCG موجود در این سامانه با عنوان **مدل داخلی تصمیم‌یار بر پایه اقتصاد بانک** ارائه می‌شود؛ در [اصطلاحات شاپرک](https://www.shaparak.ir/docs/terms) تعریف پذیرنده/ابزار پذیرش و طبقه‌بندی شبکه دیده می‌شود، اما استاندارد رسمی عمومی برای «ماتریس BCG اصناف» یا آستانه عمومی سوددهی رسته‌ها اعلام نشده است. بنابراین این طبقه‌بندی نباید به‌عنوان استاندارد رسمی شاپرک یا مجوز سوددهی یک صنف تفسیر شود.

- **سهم نسبی:** گردش ماهانه هر رسته ÷ گردش بزرگ‌ترین رسته داخلی؛ خط برش فعلاً ۵۰٪ است.
- **رشد:** تغییر گردش رسته نسبت به دوره گزارش قبلی؛ خط رشد برابر میانه رشد رسته‌های دارای داده است.
- **حاشیه خالص بانک:** کارمزد خرید کارتی استاندارد مدل + ارزش ماهانه رسوب CASA − هزینه پشتیبانی پایانه. ارزش رسوب با `(مانده × (نرخ تسهیلات − نسبت سپرده قانونی)) ÷ ۱۲` محاسبه می‌شود.
- **کارمزد خرید کارتی در مدل:** برای تراکنش کمتر از ۶٬۰۰۰٬۰۰۰ ریال، ۱٬۲۰۰ ریال؛ برای مبالغ بالاتر، `۰٫۰۲٪ × مبلغ` تا سقف ۴۰۰۰۰ ریال. هزینه پشتیبانی پیش‌فرض هر پایانه ۱٬۵۰۰٬۰۰۰ ریال در ماه است. همه این اعداد در UI به‌عنوان assumption نمایش داده می‌شوند و برای production باید با ابلاغیه جاری، قرارداد PSP و سیاست مالی بانک تطبیق و version شوند.
- **سوددهی:** حاشیه خالص مثبت «سودده»، حاشیه نزدیک به نقطه سربه‌سر «مرزی» و حاشیه منفیِ معنادار «زیان‌ده» است؛ این برچسب‌ها rule داخلی‌اند و جایگزین صورت سود و زیان، قرارداد یا تصمیم اعتباری نیستند.

## مسیرهای توسعه پیشنهادی

1. **کارت تغییر ماه و نامه شعبه:** بعد از هر واکشی، فقط رسته‌هایی که ربع BCG یا منبع‌شان عوض شده روی میز کار بیاید و یک خلاصه یک‌صفحه‌ای برای رئیس شعبه ساخته شود.
2. **شبکه تأمین قابل کشف:** از ارتباط پذیرندگان، تأمین‌کنندگان و مشتریان عمده یک گراف بسازید تا پیشنهاد SCF/GAM از روی روابط واقعی زنجیره صادر شود؛ این مورد نیازمند منبع رابطه‌ای معتبر است و از داده ساختگی تولید نشده است.
2. **حاکمیت مدل و audit trail کامل:** ورودی، دلیل پیشنهاد محصول، کاربر تأییدکننده و timestamp را در جدول رویداد غیرقابل‌تغییر ذخیره کنید.
3. **امنیت عملیاتی قبل از production:** احراز هویت سازمانی، RBAC شعبه/ستاد، rate limit، CSRF protection و masking اطلاعات هویتی را پیش از اتصال داده واقعی الزامی کنید؛ فعلاً security headerهای پایه اضافه شده‌اند.
4. **معماری رویدادمحور:** ingestion تراکنش و metric را با outbox/CDC به صف ببرید و cache داشبورد را با invalidation دقیق به‌روز کنید.
5. **بودجه‌ریزی قابل توضیح:** کنار هر نمودار سهم رسوب، کارمزد، اعتبار و هزینه پشتیبانی را با confidence interval نمایش دهید.
6. **اندازه‌گیری اثر اقدام:** برای Next Best Action آزمایش A/B، نرخ تماس موفق، نرخ تبدیل، زمان رسیدن به رسوب و بازگشت سرمایه شعب را ثبت کنید.

این سامانه تصمیم‌یار است و سقف اعتبار یا نرخ واقعی باید با سیاست اعتباری، بخشنامه‌های جاری، احراز هویت و کنترل‌های ریسک بانک تطبیق داده شود.
