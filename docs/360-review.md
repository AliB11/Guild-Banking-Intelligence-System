# بازبینی ۳۶۰ درجه — سامانه هوش بانکداری اصناف (GBI)

تاریخ: ۲۸ شهریور ۱۴۰۵ · نسخه مدل: GBI-ΠBank-1.7.0

این سند نتیجهٔ بررسی لایه به لایهٔ repository متصل به GitHub است: محصول، دامنه، موتور محاسبه، داده، UI، CI/CD، امنیت و شکاف‌ها.

## ۱. محصول

GBI یک **تصمیم‌یار بانکداری اصناف** است نه سامانهٔ Core بانکی. چهار سؤال عملیاتی را جواب می‌دهد:

1. این شبکهٔ پذیرندگان چقدر رسوب و کارمزد برای بانک می‌سازد؟
2. کدام رسته شغلی ارزش تمرکز دارد؟
3. شعبه با کدام واحد باید امروز تماس بگیرد؟
4. اگر فروش کم شود، سود و سقف اعتبار چقدر تاب می‌آورد؟

صفحه پنجم (`/sources`) تبار داده را نشان می‌دهد تا کاربر نمونه را با آمار رسمی اشتباه نگیرد.

## ۲. دامنه و قرارداد اعداد

- واحد ذخیره و محاسبه: **ریال**؛ نمایش: **تومان**.
- دوره گزارش: `YYYY-MM` جلالی؛ KPI شبکه فقط ماه‌های **منتشرشده** شاپرک (اینجا تا مرداد ۱۴۰۵).
- امتیاز سرنخ: رسوب ۳۵٪ + گردش ۲۵٪ + تناسب اعتباری ۲۰٪ + مالیات ۲۰٪.
- حاشیه خالص: کارمزد + ارزش رسوب + حاشیه تسهیلات − هزینه پایانه.
- BCG: ابزار داخلی است؛ استاندارد شاپرک نیست.

## ۳. معماری

```
مرورگر (GitHub Pages)
  صفحات Client + React Query
  client-data.ts  →  demo-data + localStorage
  compute / engine / operations   (pure)

اختیاری: Node server + PostgreSQL
  service.ts  →  همان compute
  audit + outbox روی تغییر مرحله سرنخ
```

نقطهٔ قوت: موتور pure است؛ مرورگر و سرور یک فرمول را اجرا می‌کنند.

## ۴. لایه داده

| حالت | منبع | ماندگاری |
| --- | --- | --- |
| استاتیک | ماهنامه شاپرک + طبقه‌بندی رسته + کمپین سیاستی | قیف در localStorage |
| full-stack | PostgreSQL / Drizzle | audit و outbox |

کاتالوگ منابع (`public/data/intelligence-catalog.json`) جدا از corpus واحدهاست: تبار، تقویم انتشار، اثرانگشت صفحات رسمی، ماهنامه.

## ۵. موتور محاسبه

`engine.ts` نسخه‌بندی شده است. نقاط حساس که در بازبینی‌های قبل اصلاح شده‌اند:

- ROI = حاشیه خالص / هزینه پشتیبانی (نه درآمد ناخالص).
- رشد دورهٔ اول صفر است نه درصد جعلی.
- سهم رادار از کل گردش است نه نرمال‌شده به بزرگ‌ترین رسته.
- کارمزد پلکانی بانک مرکزی به‌صورت assumption نمایش داده می‌شود.

## ۶. GitHub

| Workflow | نقش |
| --- | --- |
| `ci.yml` | lint، typecheck، catalog check، build، smoke، audit |
| `pages.yml` | static export روی GitHub Pages |
| `container.yml` | image در GHCR |
| `migrate.yml` | migration دستی با تأیید |
| `monthly-refresh.yml` | واکشی منابع پس از انتشار ماهانه اصناف |

محدودیت واقعی: رانر GitHub بیرون ایران است؛ سایت شاپرک/CBI ممکن است unreachable باشد. جاب این را ثبت می‌کند و شکست نمی‌خورد.

## ۷. UI / UX

قبل از این دور: ادبیات انگلیسی سنگین (EXECUTIVE COMMAND DECK)، توضیح کم دربارهٔ منشأ عدد.

بعد از این دور:

- راهنمای خواندن در هر صفحه
- واژه‌نامه با توضیح ساده
- برچسب تبار (نمونه / مدل / رسمی / داخلی)
- نوار تازگی داده در هدر
- ماهنامه خودکار روی میز کار

## ۸. امنیت

- حالت استاتیک داده حساس ندارد.
- قبل از production: SSO، RBAC شعبه/ستاد، CSRF، masking کد ملی.
- Headerهای پایه روی Node server هست؛ GitHub Pages آن‌ها را نمی‌فرستد.

## ۹. شکاف‌هایی که عمداً بسته نشد

- گراف زنجیره تأمین بدون داده رابطه‌ای واقعی ساخته نشد.
- ضریب اینتاکد از PDF سازمان مالیاتی parse نمی‌شود (حقوقیً و کیفیتً خطرناک).
- فهرست پذیرنده و CASA از منبع عمومی ساخته نشد. KPI شبکه از ماهنامه شاپرک است و برچسب منبع دارد.

## ۱۰. پیشنهادهای خلاقانه (پیاده‌سازی‌شده و بعدی)

پیاده‌سازی‌شده در ۱٫۶:

- دفترچه تبار داده
- تقویم انتشار جلالی با تأخیر معمول هر منبع
- واکشی اثرانگشت + پرچم بازبینی انسانی
- ماهنامه هوش اصناف بعد از چرخش ماه
- واژه‌نامه و راهنمای خواندن

پیشنهاد بعدی:

1. کارت «چه چیز این ماه عوض شد» روی میز کار
2. نامه یک‌صفحه‌ای رئیس شعبه از روی ماهنامه
3. گراف SCF وقتی داده رابطه‌ای برسد
4. اندازه‌گیری نرخ تبدیل اقدام بعدی
5. نسخهٔ سیاست کارمزد قابل تعویض از کاتالوگ بدون redeploy کد
